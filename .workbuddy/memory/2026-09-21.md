## 「加了官方分词器后准确度下降」归因（重要结论）

新增文件（用户下载）：`tokenizer.json`(34MB) / `tokenizer_config.json` / `config.json` / `rl_agent_config.json`。
`rl_agent_config.json` 是**真正的 agent 配置**：`encoder = jhu-clsp/mmBERT-base`、head_layers 2、
max_len 1024、head_max_len 256、temperature [1,1,1]、**`max_prefixes: 6`**。
`config.json` 只是**基座编码器**的 stock 配置（`ModernBertForMaskedLM`），没有 scorer/type_emb/act_head。

### 结论：不是准确度下降，而是「从不可判定变成可判定且不达标」

1. **模型卡 expect 三臂全错，且落在无信息先验上**（PRESETS[0]：expect billing/1.84/0.892/0.94）：
   - A 字节兜底：other / 1.0055 / 0.500214 / 0.500252
   - B 官方词表：other / 1.0003 / 0.502918 / 0.497276
   - R 修正▁：other / 0.9994 / 0.499907 / 0.499297
   → `noul` 精确落在 **0.500**、`score` 精确落在 **1.000**（0..2 的中点）= 模型给的是**无信息先验**。
   A 与 B 在模型卡上**无法区分**。"官方词表"没有让任何东西变差，因为**本来就没有信号**。
2. **n=120 同批局面配对检验**（2048 三项指标）：A→B 差值 合法方向 −2.5pp / merge −10.0pp / crowd −6.7pp，
   差的标准误 ±6pp → **全部不显著**。n=30 时看到的 63→73pp 波动同样是噪声。
3. **机制：argmax 在近均匀分布上完全由「prompt 几何偏置」决定，与棋盘内容无关**。实测方向分布：
   - A 字节兜底（700 tok）：up 77/120 = 64%，right 7/120 = 6%
   - B 官方词表 Ġ 编码（310 tok）：right 63/120 = 52.5%，up 29%
   - R 只把空格 token 换成 ▁（219 tok）：**right 117/120 = 97.5%，up 0%**，而此时熵 = **1.0000**、maxP = 0.2505
   → 棋盘完全相同，只改 token 几何，argmax 直方图就翻天覆地。任何 ad-hoc「准确度」都可正可负摆动 10–20pp。
4. **平凡探针也失败**（答案直白写在 state 里："the answer colour is blue"）：A 选 red、B 选 yellow。
   → 决策通道在**两种模式下都没有语义对齐**，主因是 **prompt 模板 / type_emb 注入 / head 读取位置**这类
   config.json 里根本没有、只能靠猜的重建项（`max_prefixes:6` 完全未被建模）。

### 三个已定位的真实缺陷（与准确度下降无因果，但都该修）

| 3 | `DEFAULT_CFG["rope_theta"] = 10000` line 83 | 官方 **160000** | 实测 θ=1.6e5 时 maxP 0.26→**0.82**、熵 0.99→**0.35**、合法方向 73.3→53.3、merge 50→36.7 → **「自信但错误」**，这才是真会出现「准确度明显下降」观感的开关 |

### 顺带修掉的三个「检查自身的 bug」（原本会产生误导性 PASS/FAIL）

1. `分布归一 (Σp=1)`：answer 里概率是 `round(.,6)`，11 选项求和偏差上界 = **11×5e-7**，用固定

3. `tokenizer 往返`：`prepend_scheme=always` 会多一个前导空格（官方行为），且原文案无论好坏都写

## 2048_laya.html：加规则策略（期望搜索），默认不再走模型

### 结论先行

用户要求「优先合并更多可合并数字 / 保持更多可选空间 / 优先存活 / 以突破 2048 为目标」。
做法：**默认策略换成规则（expectimax），模型降级为留痕对照**。

### 规则策略实现（写在引擎块内，可被 harness 抽取测试）

- `HEUR` 权重表：`MERGES_WEIGHT=700`（优先合并）、`EMPTY_WEIGHT=270`（保空间）、
  `MONO_WEIGHT=47`（贴边成序）、`SUM_WEIGHT=11`（抑制大块独大）、
  `CORNER_WEIGHT=150·log2(v)`（守角冲 2048）、`DEATH_PENALTY=1e7`（优先存活）。
- `lineEval` / `evalBoard`：行 + 列各算一遍线价值（rank = log2 面值）；
  `POW35`/`POW4` 预计算成数组，行/列 rank 写进复用的 `Float64Array(16)` 暂存，避免每次评估分配。
- `searchMax`（极大节点）/ `searchChance`（期望节点，2 占 0.9 / 4 占 0.1），
  带 `PROB_THRESH=1e-4` 剪枝；无合法方向返回 `-DEATH_PENALTY`。
- `ruleDecision(bd, N, {depth, prefer, band})` 返回每方向分解
  `{value, rel, merges, gained, emptiesAfter, deadRisk}` + `choice/near/order/surviveAll`。
- 三级判决：① 存活硬门（存在 `deadRisk==0` 的方向就只在其中选）
  ② 期望搜索价值 ③ 最优值 **2%** 窄带内按「合并数 → 空格数」破平。

### 实测性能与棋力（node harness，depth=2）

- 单步耗时：深度 1 < 1 ms；**深度 2 平均 2.97 ms**；深度 3 平均 640 ms（开局 1137 ms，太慢，只作离线追分）。
- 24 局基准（同种子）：**均分 36 834 / 中位 36 032 / 最低 14 716 / 21 局达成 2048 / 峰值 4096**；
  随机基线均分 1339。页面自身跑到 2048：seed `rule3` 1092 步 / 22 228 分 / 3.8 s。

### ★ 踩到的重大教训：小样本配对会骗人

| n | 「窄带择优 vs 严格取最优」配对差 |
|---|---|
| 8 | **+16 326 分，胜/负 8/0** → 差点直接写进结论 |
| 24 | **+3 253 分，SE ±5 031，不显著**；胜/负 12/12 |

n=8 的 +16k 全是噪声。2048 单局方差极大，配对差 SE 就有 ±5k 量级。
**先估 SE 再下结论**。n=24 才照出真正显著的一条：带宽放大到 ≥50%（合并压倒价值）
**显著变差 −12 869 分（SE ±3 630，胜/负 8/16）** → 合并/空间只能当破平项。

### 其他实测事实

- `prefer=merge` 与 `prefer=space` 判决**逐位相同**（分歧 0/2120 步）——「合并多」通常也「释放格子多」。
  UI 因此只保留「合并·空间优先」一个选项，引擎里保留 `space` 比较器供复测。
- 死因归因：5 局全历史「存在零风险方向却选了有风险方向」次数 = **0**，每局都只在
  「零风险方向数 = 0」时才死 → 死亡不可避免，棋力上限由估值函数决定。
- 质量守恒不变量已补进引擎单测（每步后总面值和 = 前值和 + spawn 值，20 局）。

1. `decide()` 里 `let raw = null` 声明了却**忘了在模型分支赋值**，导致「最近响应 JSON」永远走
   纯规则分支 → 完整响应 JSON 段消失。补 `raw = r;`。
2. 桩只扫 `<input>` 不扫 `<select>` → `$('strategy').value` 为空串，页面静默走了「降级」分支。
   修桩（解析 `<option selected>` + 填 `options` 数组），并给页面加 `|| 'rule'` / `|| 'merge'` 兜底。

### 架构决策：共享底座 + 场景模块 + 构建脚本

- `labs/core.js`（底座）+ `labs/template.html` + `labs/scenes/<name>.js`，

  避免 15 份页面各复制一份 ~400 行底座；场景模块只实现规则与渲染（150~350 行）。
- 底座统一提供：`Laya` 客户端（probe 同源→回退 8771）、三策略合成
  （rule 算法主判 / mix 算法筛窄带+模型破平 / model 直接判决）、留痕、
  **批量验证**（三种策略各跑 N 局给达成率对比）、指标面板。
- 场景接口：`init/legal/step/text/questions/rule/metrics/render/done/goalOk/maxSteps`。
- 构建脚本用 node 执行场景源码取 `SCENE` 的展示字段填模板，模板残留 `{{` 会直接报错。

### API 契约要点（易错）

- `POST /api/predict`：`{state, questions:[{id,type,instructions,criteria}], config}`。
- **`choice` 的 `criteria` 必须用 dict**：键就是选项，`"key: value"` 拼成选项文本。
  用数组时键会退化成 `"0","1",…`，模型看到的是无意义下标（已写进 README）。
- 响应：`answers.<id>.{choice,confidence,probs,ranking,logit_spread}`（choice）、
  `{score,argmax_level,probs,levels}`（score）、`{noul,p_no}`（noul）。
- 15 个场景的 `logit_spread` 实测只有 **0.0009~0.024** → 再次印证决策通道未对齐，
  所以默认 `rule` 主判、模型仅留痕对照，这个设计在 15 个场景上都成立。

### ★ 本轮踩到的 6 个真 bug / 陷阱（都是「看起来能跑但其实错」）

1. **`maxSteps` 上限过小会把「没死」误判成「没达成」**。贪吃蛇上限 400 步时样本外均长 37，
   改成 2400 后是 63.5 —— 蛇长到 50 需要 300~500 步，填满 100 格要 2000+ 步。
   打砖块同理：45 块砖要 2400+ 决策步，上限 1200 时看起来像「漏球」，其实只是没打完。
2. **小样本调参必然过拟合**（与 2048 那次同源）。贪吃蛇权重用 12 局坐标下降扫出
   训练 66 → 样本外只有 37；换 48 局全新 seed 终裁才稳（64.5±3.3，达成 32/48）。
   调参样本量必须 ≥ 48，且必须用「没参与扫描的 seed」复核。
3. **位掩码超过 32 位静默出错**。Lights Out 用 Number 位运算，6×6=36 格溢出，
   4/5 阶全对、6 阶全错（表现为 20/30 而不是 0/30，极易看漏）。改用 BigInt。
   配套坑：`0n !== 0`，测试里 `mask === 0` 要写成 `=== 0n`。
4. **前瞻模拟假设「之后不再操作」会与实际控制频率不一致**。Flappy 用「扇一次后自由落体
   40 帧」评分，实际每 6 帧能再扇一次，于是鸟一路撞顶（通过 0 个管道）。
   改成阈值规则 + 「扇完最高点不得越过缺口上沿」约束。
5. **物理参数会让局面根本不可解**。Flappy 管道间距 150px = 50 帧，而相邻缺口落差可达
   460px，全速上升也来不及（卡在 9 个管道）。放大间距到 235px + 限制相邻落差 130px 才达标。
6. **终局索引越界**：股票 `i == n` 时 `prices[i]` 是 undefined → 净值变 NaN（不是报错，
   是静默污染所有统计）。取 `Math.min(i, n-1)`。

另外两个「断言写错」而非代码错：迷宫是完美迷宫（无环、路径唯一），所以 DFS 也必然等于
BFS 最短路，不能断言「DFS 应更长」；打砖块球上升期直接返回当前 x 会让挡板乱跑，
必须一路模拟到球真正下落到挡板高度（含顶墙反弹）。
